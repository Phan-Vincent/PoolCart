Prioritized findings

Critical — No effective pool membership, identity, or host authorization boundary.
Existing; the new RPC extends the problem.

Evidence: supabase/schema.sql:209–229 permits all operations with unconditional policies. The RPC accepts caller-supplied identity and runs as SECURITY DEFINER at 92–104, inserting that identity at 142–148. src/services/repository.ts:237–242 fetches every pool and related table. App.tsx:915–924 exposes host operations without checking the active user’s membership or role.

Trigger/impact: A non-host can use the normal UI to lock a pool, change others’ payment states, or cover shares using the host’s identity. An API role with table privileges faces no row-level restriction on reading addresses/messages or modifying other pools. Actual deployed grants were not supplied; unconditional policies do not themselves grant table privileges. PostgreSQL documents this distinction. 
postgresql.org

Additionally, claims have separate pool/item foreign keys but no constraint requiring the item to belong to that pool, and no participant foreign key (schema.sql:60–68). The loader associates claims by item alone (repository.ts:272–279), allowing inconsistent rows to affect another pool’s calculations.

Fix: Bind identity to authenticated users; enforce membership and host permissions in policies and RPCs; derive the claimant identity server-side. Restrict direct financial/order mutations and add composite relationship constraints. Remove demo identity switching from shared production use.

A second defect occurs with seven $3 shares in six-unit cases: the pool has $18 committed and $3 pending, but caseFilled = remainderUnits === 0 makes all $21 pending in participant breakdowns (141–147). There is no allocation identifying which six shares ship.

Delivery rounding also lacks reconciliation: a $20 fee split three ways becomes three displayed/payment amounts of $6.67, totaling $20.01 (98–100; SplitLedgerView.tsx:35).

Impact: Premature minimum/free-delivery claims, payment requests for unshipped goods, inaccurate pickup lists, and unmatched balances. Lock/export does not require resolution (HostOrderSheetView.tsx:86–96, 173–178).

Fix: Base supplier eligibility on orderable merchandise. Allocate committed versus pending quantities per participant deterministically. High — The new RPC silently rejects every first claim; a null delta can delete an existing claim.
New function defect; not reached by the current claim buttons.

Evidence: supabase/schema.sql:150–176.

Trigger: Call claim_item_share with p_delta = 1 for a user who has no claim row.

SQL reasoning: SELECT coalesce(quantity, 0) INTO ... FROM item_claims returns no row, so the target becomes null; the inner coalesce never runs. PostgreSQL’s greatest(0, NULL + 1) then returns zero because it ignores null arguments. These semantics are documented. 
postgresql.org
+1

Impact: The RPC creates/updates the participant, takes the delete branch, and returns zero quantity without an error. Repeated attempts remain ineffective. Previous-total-dependent metadata can be null despite the TypeScript boolean contract. Passing a null delta for an existing claimant similarly computes zero and deletes their claim.

Fix: Coalesce the lookup result after selection, or coalesce a scalar subquery. Explicitly reject null/invalid deltas and required identifiers before writes. Verify first claim, removal to zero, and re-claim after removal.

High — “Drop Partial” can erase valid claims and has no stable allocation order.
Existing.

Evidence: App.tsx:414–435 removes quantities from the reversed claims array. Cloud claims are loaded without ordering (repository.ts:241). syncItemClaimsList separately deletes all item claims and then upserts the client’s remaining list (670–685); it ignores the delete result.

Trigger/impact: Delete succeeds, then replacement upsert fails: valid full-case claims are gone. Alternatively, another participant claims after the host’s snapshot but before deletion; that claim is removed without appearing in the replacement. Which participant loses the partial allocation can change after reload because array order is not a persisted claim priority.

Fix: Resolve partial cases in one server transaction under the same locks as claims. Use a documented, persisted allocation order; calculate from current rows; return the resulting allocation. Any failure must roll back the entire operation.

High — The sync lifecycle can discard accepted local work, restore stale state, and conceal failed writes.
Existing.

Evidence and deterministic triggers:

Local-to-cloud loss: Create a local pool, then connect to an empty backend. repository.ts:250–253 seeds INITIAL_POOLS, not local work, and overwrites the local cache. Connecting to a populated backend also replaces that cache (333–334).
Out-of-order refresh: Start refresh A, commit a new claim, complete refresh B with the new state, then let A return older rows. App.tsx:76–84 accepts A unconditionally. Repository cache writes also lack ordering/version protection.
False completion: Pool/item/message/status writes update the UI and cache first, but their returned errors are discarded (App.tsx:265–270, 347–352, 543–559, 581–586). There is no retry queue or rollback.
Pickup never syncs: App.tsx:589–602 only saves locally. A later cloud load replaces the checkbox with picked_up from the database (repository.ts:266).
Hidden read failure: msgsRes.error is omitted from the error checks (repository.ts:237–248), allowing failed chat reads to appear as an empty successful result.

Impact: Lost pools/messages/claim changes, misleading success, and pickup records reverting. These are source-demonstrable failure paths; their real-world frequency is unmeasured.

Fix: Define an explicit local-import policy; namespace caches by backend/account; sequence or version refreshes and mutations; preserve pending operations until acknowledged. Handle every repository error, persist pickup changes remotely, and expose subscription health instead of inferring “Realtime Connected” from a successful fetch.
